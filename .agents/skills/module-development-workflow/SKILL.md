# 模块开发流程

当用户要求新增业务模块，或实现涉及多个文件、多个层次的功能时使用本 Skill。简单修复、单文件小改动和纯文档编辑不强制使用完整流程，除非用户明确要求。

## 目标流程

将一个不完整的需求推进到可验证的实现：

```text
需求访谈与收集
  -> 结构化 PRD 初稿
  -> 设计文档与 CRUD 契约
  -> 用户确认设计文档
  -> 技术文档
  -> 用户确认技术文档
  -> 实施文档
  -> 用户确认实施文档
  -> 子代理实施拆分
  -> 子代理开发
  -> 主代理集成
  -> 自动化验证
  -> Smoke Test
  -> 交付记录
```

全程遵守仓库现有架构、包管理器、测试约定、审批门槛，并保护用户已有的未提交修改。

## 严格串行审批门槛

新增业务模块必须严格按以下顺序推进，不能提前生成下一阶段文档或修改业务代码：

1. 先完成需求访谈，编写设计文档和对应的 CRUD 契约；两者都标记为“待用户确认”。
2. 用户明确确认设计文档和 CRUD 契约后，才能编写技术文档。
3. 用户明确确认技术文档后，才能编写实施文档。
4. 用户明确确认实施文档后，才能创建或修改 Entity、DTO、Controller、Service、Module、Guard、Migration、Seeder、测试和配置代码。
5. 每个阶段只提交当前阶段允许的文件；不得为了“提前准备”而创建后续阶段文档或代码。

“已确认”“开始实现”“按此方案”等明确答复才算通过当前门槛。仅提出需求、补充字段、讨论方案或要求继续整理，不视为审批通过。

每个审批节点必须向用户说明：

- 当前正在审批的文档；
- 已确定的范围、权限、数据和 API 决策；
- 未解决的风险或待确认项；
- 获得确认后下一步将生成的唯一内容。

如果用户要求修改已确认阶段，回到受影响的最早阶段重新审批，并同步将后续文档标记为待确认；不得直接修改代码绕过审批。

## 需求与结构化 PRD 的先后顺序

结构化 PRD 应建立在需求讨论的基础上，而不是在完全不了解需求时直接编写完整文档。

执行顺序：

1. 先通过需求访谈或对话明确用户、问题、目标、核心流程和优先级。
2. 根据已知信息整理结构化 PRD 初稿，包含目标、范围、角色、功能、验收标准和非目标。
3. 对无法从需求中确定的内容标记为“待确认”，不得把代理的假设写成已确认需求。
4. 由用户确认 PRD 的范围、关键业务规则和优先级。
5. 需求确认后，再编写技术文档、拆分实施任务和开始开发。

需求讨论过程中可以先建立 PRD 骨架并持续补充，但在确认前必须明确标注文档为草案；如果关键范围、数据、权限或兼容性规则仍有歧义，应暂停实现并集中提问。

## 阶段一：项目调查

修改代码前必须：

1. 阅读仓库的 `AGENTS.md`、README、包清单和相关模块文档。
2. 检查 Git 状态，不回滚无关改动。
3. 搜索本地依赖和已有模块，优先复用现有能力。
4. 对计划使用的库、框架、SDK 或服务阅读官方文档。
5. 确认运行时、模块系统、编译器、包管理器、数据库和测试约束。
6. 对后端 API 输入校验，检查项目已安装的 Zod 版本、Nest `StandardSchemaValidationPipe` 与现有 schema 绑定方式；沿用项目实现，不另引入校验库或重复管道。

会影响设计的假设必须明确记录，不要把其他项目的约定静默带入当前仓库。

### 业务模块目录约束

业务模块的首要结构目标是根目录清晰、职责可扫描，而不是单纯减少文件数量。每个业务模块独立维护自己的职责目录，禁止建立跨业务模块共享的全局 `entity/` 或 `spec/` 目录：

```text
<module>/
  <module>.module.ts
  controller/
  service/
  entity/
  dto/
  spec/
```

仅在存在对应文件时创建目录。业务能力包含多个紧密协作文件时，可使用 `context/`、`history/`、`trace/` 等表达业务意图的目录；不要把不同职责全部塞进一个 Service，也不要为了单个文件机械增加目录。目录整理必须保持模块边界、依赖方向和 API 行为不变。

目录迁移时需要同步检查：

- import 和相对路径；
- Nest Module 的 providers、controllers、imports、exports；
- MikroORM Entity 注册和迁移配置；
- 测试发现路径；
- 文档中的目录树和文件路径；
- 是否存在跨模块引用私有实现。

## 阶段二：确认范围

将需求整理为：

- 模块名称和所有权边界；
- 用户操作、API 或事件契约；
- 明确的非目标；
- 数据、权限和持久化要求；
- 兼容性和迁移约束；
- 验收标准。

需求过大时，先收窄为最小可用里程碑。后续能力记录在后续计划中，不提前实现。

## 阶段三：按业务编写文档

同一业务的文档放在同一个目录：

```text
docs/modules/<业务名>/
  <模块名>-design.md
  <模块名>-technical.md
  <模块名>-implementation.md
```

使用 [module-doc-template.md](references/module-doc-template.md) 作为起点：

- 设计文档：说明做什么、边界、API 行为、数据规则和非目标。
- 技术文档：说明目录、依赖、接口、状态、错误、安全和测试；涉及 API 输入时，列出 Body、Query、路由参数对应的 Zod schema、输入与输出类型、转换/默认值/未知字段策略，以及 Nest Pipe 的 400 错误映射。
- 实施文档：说明子代理分工、文件所有权、集成顺序和验收流程。

文档必须串行创建：先写设计文档和 CRUD 契约，等待用户确认；确认后再写技术文档，等待用户确认；确认后再写实施文档，等待用户确认。任何文档未获确认，都不得创建下一份文档或开始实现。

## 阶段四：使用子代理分工

对于较大的模块，在协作能力可用且用户或仓库流程要求分工时，使用独立子代理处理边界清晰的任务。常见拆分：

- 依赖、配置和基础设施；
- 核心领域、应用服务和模块接入；
- 测试、测试替身和测试基础设施。

按 [仓库的子代理阅读范围](../../../AGENTS.md#子代理阅读范围) 派发任务。给每个子代理明确说明：

- 任务目标、源码入口和允许搜索、读取的路径；
- 已确认的契约要点及需要阅读的文档章节；
- 负责修改的文件；
- 禁止修改的文件；
- 需要阅读的本地和官方文档；
- 验收标准；
- 完成后的报告格式。

禁止两个子代理同时拥有同一文件的写权限。根配置、锁文件、应用模块注册和 CI 配置等公共文件默认由主代理维护。

每个子代理完成后必须报告：

```text
修改文件
执行命令
测试结果
未解决风险
越界修改
```

如果任务规模不足以使用子代理，应说明原因，但仍保持文档、边界和验证纪律。

## 阶段五：实现和集成

主代理负责：

1. 解决依赖版本和 API 冲突。
2. 整合子代理修改，不能回滚用户工作。
3. 维护公共文件和跨模块接线。
4. 检查模块边界、导入方向、配置处理和安全行为。
5. 新增必要中文注释，避免无意义逐行注释。
6. 按仓库规则增加测试和包脚本。
7. 对后端 API 请求，将各自的 Zod schema 放在所属模块的 DTO 目录，并在 Controller 参数装饰器上绑定 schema；禁止把校验规则留在 Controller 手写判断中。

优先使用项目已有抽象和成熟库。已有能力足够时，不重复造轮子。

## 阶段六：验证

根据风险执行验证；较大的模块至少运行：

```text
格式检查
类型检查
构建
所属包测试
仓库检查命令
差异检查
```

运行时依赖可用时，再对主要用户路径执行手工 Smoke Test。基础设施不可用时必须明确说明，不能把未执行的检查写成已通过。

至少验证：

- API 和认证授权行为；
- Zod schema 与 Nest 参数绑定：合法输入、非法边界、未知字段拒绝、默认值/转换结果及 400 错误映射；
- 密钥不会返回或写入日志；
- 没有意外持久化、迁移或业务耦合；
- 自动化测试不依赖真实凭据，除非明确标记为 Smoke Test。

## 阶段七：交付

最终汇总：

- 已实现和明确排除的范围；
- 修改的文件和模块；
- 子代理分工及报告；
- 依赖和配置变化；
- 验证命令和结果；
- 剩余风险和后续工作。

只完成文档或计划时，不得宣称功能实现完成。
