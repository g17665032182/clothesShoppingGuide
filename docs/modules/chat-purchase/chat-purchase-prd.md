## 问题与目标

聊天已经能够展示真实商品卡片，后端也已提供规格查询、创建订单和模拟支付接口，但卡片没有购买入口，助手不能收集购买信息，前端没有本人订单页面。

本轮打通“点击商品购买 → 聊天补齐信息 → 确认卡提交 → 待支付订单 → 主动模拟支付 → 查看和处理本人订单”。订单实际持久化并预占本站库存，支付不会产生真实扣款。

## 核心流程

1. 点击某张商品卡的“购买”，以明确商品标识发起本会话草稿。
2. 服务端查询当前真实规格，助手询问尚未明确的颜色、尺码、数量和收货信息。
3. 信息完整且商品当前可售后，展示服务端生成的确认卡。
4. 用户可继续聊天修改；每次有效修改使旧确认卡失效。
5. 用户点击“确认下单”，服务端核对草稿版本、规格、价格和库存，原子创建订单并关联草稿。
6. 返回待支付订单卡，展示订单号、实际金额、支付截止时间和“模拟支付”。
7. 用户可在聊天订单卡或“我的订单”处理订单，后续履约沿用已有后端规则。

下单前变价必须展示新价格并重新确认；缺货或下架时让用户自行修改规格、数量或重新选商品。网络结果未知时先核实或重试同一次提交，不能另起一次购买。

## 范围与非目标

本轮包含聊天购买草稿持久化、真实规格查询接入、聊天补齐和修改信息、结构化确认卡、按钮提交、聊天订单卡及本人订单页面。

本轮不包含真实支付、外部电商代购、多商品合单 UI、购物车、地址簿、长期保存地址偏好、退款退换货、订单内容编辑、拆单发货、物流轨迹、自动收货、助手执行订单写操作。

后端现有多 SKU 下单 API 保留，本轮购买入口只生成单 SKU 订单。订单后续状态、库存及管理员发货规则不重新定义。

## 验收标准

以下为整体验收清单，不因代码集成而批量勾选。后端、迁移及 fake 模型链路的自动化证据和登录态/移动端浏览器缺口分别记录在[实施文档](./chat-purchase-implementation.md#实际交付记录2026-11-08)。

- [ ] 从商品卡开始可完整走通单 SKU 聊天购买，不依赖手工输入 SKU 或复制商品链接。
- [ ] 多规格必须由用户明确选择，唯一可售规格及默认数量在确认卡可见。
- [ ] 缺失、歧义或非法字段阻止提交，不将模型推测当作用户事实。
- [ ] 草稿刷新恢复、24 小时截止、不同账号与不同会话隔离正确。
- [ ] 更换商品需明确放弃原草稿；放弃不影响已创建订单。
- [ ] 旧确认卡、变价、缺货、下架、并发修改均不能绕过重新确认。
- [ ] 按钮提交重复、断网重试和提交后刷新只关联一张订单。
- [ ] 普通聊天文本和模型工具不能触发订单创建、支付、取消或收货。
- [ ] 本人订单列表、详情和各状态按钮正确，越权不能读取或操作他人订单。
- [ ] 无真实扣款，模拟支付标识明确；30 分钟期限以服务端为准。
- [ ] 收货信息不进入长期记忆、其他会话默认草稿或公开工具调试信息。
- [ ] 旧聊天、商品推荐、分页和管理员功能保持兼容。
