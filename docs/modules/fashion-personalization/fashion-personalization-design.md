# 个性化商品与穿搭推荐设计文档

## 状态与上下文

- 状态：已确认；实施中
- 业务目的：让用户通过 LLM 描述风格、场合和预算后，搜索真实可访问的服装商品，组合成潮流、复古、洛丽塔等风格的穿搭建议，并根据反馈持续改善个人及相似需求的推荐。
- 所属应用：后端 `apps/api`；聊天交互位于 `apps/web`。
- 需求来源：用户希望 LLM 在每次推荐后了解用户满意程度，形成可复用的推荐记忆，并在下次相同或相近需求中更快给出合适结果。
- 关联模块：`chat-records`、`product-catalog`、`user-preferences`、`user-memory`、`llm`。
- 关联契约：[个性化商品与穿搭推荐 CRUD 契约](../../contracts/fashion-recommendation-crud-contract.md)。
- 最后更新：2026-11-22。

用户已确认本设计及对应 CRUD 契约，并于 2026-11-22 确认技术方案和实施文档；同日确认按本文已有推荐采纳 D1-D9 的设计取向，并将拼多多、淘宝列为在线来源优先候选。当前进入代码实施，在线来源仍保持关闭。

现有项目已经区分结构化穿衣偏好与 Markdown 长期记忆。结构化偏好由用户本人维护，LLM 只能读取；Markdown 记忆可以保存用户明确表达的穿衣背景。新增推荐反馈不能绕过这两个边界，也不能把模型对用户的猜测直接写入任一资源。

## 目标与范围

### 首期目标

1. 用户可以用自然语言描述风格、场合、季节、预算和其他穿衣要求，例如“想要复古一点的约会穿搭”或“找一套甜系洛丽塔风格”。
2. 系统将需求解析为结构化的推荐意图和若干商品检索任务，从已接入的本地或在线商品源获取真实商品；LLM 不得把通用穿搭知识伪装成在售商品。
3. 系统先按硬条件过滤商品，再按风格、场合、颜色、版型和个性化信号排序；每个商品都保留来源、观测时间和可验证属性。
4. 系统按穿搭槽位组合候选商品。现有目录可覆盖上衣、下装、连衣裙、外套和鞋；缺少商品源支持的配饰只可作为非商品建议，不能伪造商品卡。
5. 用户可查看单品推荐，也可查看整套方案。整套默认采用“连衣裙 + 鞋/外套”或“上衣 + 下装 + 鞋/外套”的搭配结构；返回套数和每槽位候选数由技术阶段确定。
6. 每套方案展示风格说明、单品卡片、可验证匹配理由、商品来源、当前价格/币种、可用状态、观测时间和商品链接。总价只在同币种且所有金额均可验证时展示。
7. 用户可以对整套方案、某个槽位或单件商品表达“合适/不合适”，并选择有限的不满意原因，例如风格、颜色、价格、场合、版型或“太夸张/太普通”。
8. 系统把反馈与本次推荐意图、展示过的商品、穿搭方案和会话消息建立关联；后台形成个人派生推荐画像，并为后续阶段预留相似需求的匿名聚合接口。
9. 后续推荐使用个人画像和达到最小样本门槛的相似需求统计作为软排序信号；当前轮明确要求、预算、尺码和有货条件始终优先。
10. 用户可以查看、关闭和清空个人派生推荐画像。跨用户统计不展示个人来源，不允许从小样本统计反推个人。

### 分阶段发布建议

- 首发打通“LLM 需求解析 -> 本地目录检索 -> 单品候选 -> 穿搭组合 -> 结构化推荐卡 -> 显式反馈”完整用户链路。
- 在线商品源以独立适配器接入，不改变本地目录的商品事实边界；首期不启用在线来源，拼多多和淘宝作为后续优先调研/接入候选，授权、平台接口、地区、币种和结果上限另行确认。
- 个人画像基于该用户的多次显式反馈更新。
- 首期不启用跨用户匿名汇总，也不采集仅用于未来聚合的跨用户明细；第二阶段单独确认最小样本量、去标识化、删除延迟和退出规则。
- 首期只使用显式反馈学习，不接入收藏、购买、点击等隐式行为；商品来源适配、来源可信等级和统计生命周期按后续阶段单独确认。

### 明确不包含

- 不自动创建、修改或删除 `user-preferences` 中的结构化偏好。
- 不把助手推测、商品原始网页文本、模型思维过程或完整聊天记录写入推荐画像。
- 不使用 IP、设备、浏览器指纹或未明确提供的身份/位置推断用户风格。
- 不因为一次点击或一次负面反馈永久改变推荐策略。
- 不让 LLM 直接决定用户反馈记录中的 `userId`、商品归属或推荐结果事实。
- 不在首期引入向量数据库或复杂协同过滤；先使用可解释的规则排序和有界统计。
- 不以未选定的外部 MCP/API 作为已接入能力；供应商和平台覆盖范围需单独确认。
- 不代替实时商品查询；价格、库存、商品链接和在售状态必须来自当前可信商品来源，并标明信息来源及观测时间。
- 不承诺覆盖目录/供应商未提供的配饰或尺码；缺失商品槽位须明确标记，不得用生成内容填充商品事实。
- 不把商品源的搜索摘要、模型生成的品牌/价格/库存或未经验证的链接当作商品事实。

## 用户角色和权限

| 角色         | 能力                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| 已登录消费者 | 提交本人反馈、查看本人派生推荐画像、关闭或清空本人推荐学习                   |
| 未登录访客   | 不建立长期推荐画像；可以继续使用未登录范围内的非个性化能力（如未来另行确认） |
| 管理员       | 首期不能查看个人反馈原文、个人画像或跨用户明细                               |
| 后台任务     | 仅处理已授权且通过字段白名单校验的反馈候选，不绕过用户隔离                   |

## 核心流程

### 推荐链路

1. LLM 根据当前消息和已允许注入的个人上下文生成结构化推荐意图。意图只包含用户表达或服务端已有的条件，不接受模型提交的用户 ID、商品事实或价格。
2. 推荐编排层把意图拆成一个或多个有界的商品检索任务，例如“复古约会”可能查询连衣裙、鞋和外套；每个任务包含槽位、类别、硬条件、软标签和预算分配。
3. 商品目录或已批准的来源适配器按硬条件查询商品，并返回规范化商品投影：名称、类别、图片、价格、币种、库存布尔值、来源、观测时间、详情 URL 和服务端验证标签。
4. 编排层合并去重候选，剔除来源不可信、价格/库存缺失或不满足硬条件的商品；不得以生成文本补齐缺失字段。
5. 穿搭组合器按槽位、颜色协调、风格一致性、场合适配、预算总额和商品可用状态生成有限数量的整套方案。组合器只处理已返回的商品投影，不访问商品 Entity。
6. 聊天服务为本轮生成推荐组、单品项和整套方案引用，将结果通过现有卡片安全投影展示；商品卡保持兼容，整套方案需要新增或扩展受控卡片模板，具体字段待技术阶段确定。
7. 前端展示单品与穿搭方案，并在每个反馈目标旁提供低打扰入口。商品链接、来源和观测时间必须可见或可展开查看。
8. 服务端校验推荐组、消息、商品/方案引用和当前认证用户的归属后保存反馈事件。
9. 后台任务按用户和会话合并短时间内的反馈，更新派生推荐画像；画像更新失败不影响已经生成的商品回答。

### 下一次推荐

1. 当前用户消息和本轮明确条件优先。
2. `user-preferences` 提供用户主动维护的结构化事实。
3. 推荐画像只提供软排序信号，例如“更偏好复古”“不喜欢过度甜美”。
4. `user-memory` 只提供与当前问题相关、且由用户明确表达的背景。
5. 商品查询服务重新校验实时价格、库存和链接。
6. LLM 解释匹配原因时，只能使用服务端返回的商品属性和推荐信号，不编造事实。

## 商品检索与来源适配

### 统一商品来源投影

所有商品源都必须先转换为统一的服务端投影，再进入排序或穿搭组合。投影至少包含：

- `sourceId`、`sourceName` 和 `sourceType`，用于区分本地目录、在线 API 或未来的 MCP 适配器；
- 稳定的来源商品引用和可选 SKU 引用；模型和客户端不能自行生成；
- 商品名称、类别、品牌（如来源明确提供）、图片 URL 和详情 URL；
- 当前价格、币种、可用状态和 `observedAt`；缺失或过期信息不能伪装成当前事实；
- 来源明确提供的风格、场合、颜色、版型等公开标签；
- 服务端生成的有限匹配标签，不包含模型自由发挥的属性。

来源适配器负责认证、限流、错误映射、字段白名单、来源条款和缓存策略。推荐模块只依赖统一 Port，不依赖具体供应商 SDK、网页 DOM 或来源私有响应。

### 结果可信度与失败

- 本地目录是当前已确认的首发来源，沿用 `product-catalog` 的实时价格、可售状态和匹配标签规则。
- 在线来源只有在单独确认平台覆盖、授权方式、调用预算、结果页数和缓存/刷新周期后才能开启。
- 来源不可用时，系统可以返回其他可用来源或仅返回非商品化穿搭建议，但必须明确说明商品结果不完整；不能把模型知识当作替代商品源。
- 混合来源的价格只在同币种且各来源观测时间满足策略时计算总价；否则分别展示，不计算总价。
- 同一商品跨来源去重只能使用来源明确的稳定标识或服务端确认的规范化键，不能仅凭名称相似就合并。

## 穿搭组合规则

### 槽位与方案

每个推荐组包含一个推荐意图和若干候选目标。目标类型至少包括：

- `item`：单件商品推荐；
- `outfit`：由多个商品项组成的整套方案；
- `slot`：整套方案中的上衣、下装、连衣裙、外套、鞋等位置。

首期只使用现有商品类别。配饰、妆容、发型和搭配动作可以作为文字建议，但没有真实商品投影时不生成可点击商品卡。

### 排序信号

组合排序按以下顺序处理：

1. 当前轮硬条件：预算、尺码、明确颜色/类别、可用状态；
2. 槽位完整性和商品来源可信度；
3. 当前轮风格、场合、季节、颜色与版型匹配；
4. 用户主动维护的结构化偏好；
5. 个人派生推荐画像；
6. 达到门槛的匿名聚合信号；
7. 稳定的来源排序键和商品外部标识。

任何软信号都不能覆盖硬条件。无法补齐整套槽位时，返回已满足的部分并明确缺失槽位，询问用户是否接受单品建议或放宽条件。

## 反馈与推荐画像

### 反馈事件

反馈事件至少包含：

- 当前认证用户和会话/消息归属；
- 服务端生成的推荐组引用和目标引用（整套方案、槽位或单品）；
- 当前搜索意图的安全快照：风格、场合、预算区间、季节等；
- 商品公开标签的安全快照；
- 反馈类型：`positive`、`negative`、`dismissed`，后续可增加 `saved`、`purchased`；
- 可选原因码和用户短文本；
- 创建时间、来源和幂等键。

用户短文本只作为受限反馈依据，不直接作为完整长期记忆保存。敏感信息、联系方式、详细地址、凭据、图片内容和原始供应商载荷不得进入反馈事件。

### 派生推荐画像

画像只保存经过校验的汇总结果，例如：

- `preferredStyles`：偏好风格及置信度；
- `avoidedStyles`：倾向避开的风格及置信度；
- `preferredOccasions`：更常接受的场合；
- `priceSensitivity`：价格敏感度的有限枚举；
- `silhouetteSignals`：版型或搭配倾向；
- `evidenceCount`、`updatedAt` 和画像版本。

画像中的置信度必须受证据数量和反馈权重限制。一次反馈只能形成候选信号，不能直接成为高置信度长期事实。用户明确的当前需求可以覆盖画像；用户明确纠正时，旧信号应降权或失效。

### 反馈权重

首期建议采用保守顺序：

1. 用户明确文字反馈：强信号；
2. 用户点击“合适/不合适”：中强信号；
3. 收藏、购买或继续查看：中等信号，需在后续业务确认后接入；
4. 仅展示或曝光：不作为满意度信号。

不能仅根据模型生成了回答，就推断用户满意。

## 跨用户匿名汇总

跨用户汇总属于后续阶段，必须满足以下条件后才启用：

- 只使用去标识化的风格/场景/价格桶和商品标签；
- 设定最小样本量，低于门槛不发布统计结果；
- 不保存可回溯到单个用户的明细查询；
- 用户可以关闭推荐学习，关闭后不再产生新的个人反馈学习数据；
- 个人删除或清空不应暴露其曾经参与某个小样本分组；
- 汇总结果只用于排序和冷启动，不直接向用户展示“其他用户喜欢你”之类的结论。

## 模块边界

- `fashion-personalization` 负责推荐组/穿搭方案引用、反馈事件、派生推荐画像、反馈设置和匿名汇总的公开端口。
- `chat-records` 负责把当前推荐组与聊天消息绑定，并调用公开反馈登记端口；不直接访问推荐模块的 Entity 或 Repository。
- `product-catalog` 负责商品、SKU、实时有货状态、价格和可验证匹配标签。
- `user-preferences` 负责用户主动维护的结构化偏好；推荐模块只能读取公开端口。
- `user-memory` 负责用户明确表达的长期背景；推荐模块不写入记忆文档。
- `llm` 负责工具编排和语言表达，不拥有推荐反馈写权限。
- `apps/web` 负责反馈控件和画像设置页面；写操作通过认证 API。

禁止跨模块引用私有 Entity、Repository、DTO 或实现目录。推荐模块不能成为聊天模块或商品模块的隐式数据库访问旁路。

## API 或事件契约概览

首期拟提供：

- `POST /api/fashion-recommendation/feedback`：提交本人对推荐组、整套方案、槽位或商品的反馈。
- `GET /api/fashion-recommendation/profile`：读取本人派生推荐画像摘要。
- `DELETE /api/fashion-recommendation/profile`：清空本人派生画像和未汇总的个人反馈学习数据。
- `GET/PATCH /api/fashion-recommendation/settings`：读取或关闭推荐学习开关。

聊天内部只使用窄端口：

- 登记推荐组引用；
- 登记本轮商品/方案的安全来源引用和展示快照；
- 登记经过服务端校验的反馈；
- 读取当前用户、当前需求相关的推荐上下文。

这些内部端口不作为普通 LLM 工具公开，不接受模型提供的用户 ID、商品价格、库存或推荐事实。

## 错误、幂等与删除

- 未登录：`401`。
- 推荐组、消息或商品不属于当前用户/当前会话：统一 `404`，不暴露存在性。
- 反馈字段非法、未知字段或原因码不匹配：`400`。
- 同一用户对同一推荐项重复提交相同反馈：幂等返回，不重复增加证据。
- 画像更新失败不影响聊天回答；反馈任务可安全重试。
- 关闭推荐学习后不读取画像、不登记新学习事件；不自动删除用户手动维护的偏好和记忆。
- 清空画像必须使排队任务失效，防止旧任务回写；具体 generation/租约机制沿用用户记忆模块的保护思路。
- 删除聊天会话不自动删除已经形成的推荐画像；若用户清空推荐画像，相关原始反馈学习记录按契约处理。

## 决策记录

用户于 2026-11-22 确认按本文已有推荐采纳以下设计取向：

- D1：首期提供“合适/不合适”和少量固定不满意原因码。
- D2：派生画像无需逐条确认即可参与排序，但只能作为软信号，并支持查看、关闭和清空。
