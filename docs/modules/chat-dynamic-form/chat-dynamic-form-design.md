# 聊天动态表单设计文档

## 状态与上下文

- 状态：原设计及 2026-11-13 确认的地址选择卡片/空地址簿表单联动已实施；登录态浏览器验收未执行。
- 业务目的：当聊天助手需要结构化收集用户信息时，生成受约束的动态表单描述，由前端卡片渲染并在用户确认后提交到服务端业务处理器。
- 所属应用：`apps/api`、`apps/web`。
- 所属模块：`chat-records` 负责会话事件与展示绑定；动态表单模块负责协议校验、表单实例和提交编排；具体业务模块负责字段语义及最终写入。
- 最后更新：2026-11-13。
- 关联文档：[动态表单 CRUD 契约](../../contracts/chat-dynamic-form-crud-contract.md)、[流式聊天 CRUD 契约](../../contracts/chat-streaming-crud-contract.md)、[聊天卡片展示设计](../chat-card-display/chat-card-display-design.md)。

## 目标与范围

目标流程：

1. 助手根据当前任务判断需要收集的字段。
2. 助手调用通用动态表单工具，提交表单用途、受限字段定义和业务意图标识。
3. 服务端校验字段定义、业务意图和当前用户/会话归属，生成安全的表单 JSON。
4. 服务端通过独立 `form` SSE 事件向前端发送表单定义；事件不携带模型原始工具参数。
5. 前端按字段注册表渲染表单卡片，用户填写并点击确认。
6. 前端将表单值提交到服务端；服务端按已注册的业务处理器再次校验并执行。
7. 提交结果以结构化结果返回前端，并可继续进入当前聊天上下文。

首个业务接入为购买信息收集：表单可以收集规格、数量、收件人、手机号和收货地址，但提交只能更新当前本人购买草稿，不能直接创建订单。

购买草稿缺少收件信息时，先查询本人地址簿；非空时通过前端地址选择卡片让用户选择，只有查询成功且地址簿为空时，才通过 `request_dynamic_form` 生成 `purchase_recipient` 表单。查询错误及卡片数据隔离见[用户信息查询工具设计](../chat-user-information/chat-user-information-design.md)和[购买契约](../../contracts/chat-purchase-crud-contract.md)。

本设计不允许模型直接提交用户填写值、不允许模型创建订单或执行其他正式业务动作，也不允许表单定义携带任意 URL、脚本、组件名、数据库字段名或校验代码。

## 用户与权限

| 角色       | 能力                                                               |
| ---------- | ------------------------------------------------------------------ |
| 已登录用户 | 查看本人会话中的表单、填写、修改、确认提交                         |
| 聊天助手   | 提议本轮需要收集的字段；不能读取用户未提交的字段值或绕过业务处理器 |
| 前端       | 只渲染服务端确认的字段类型和选项；不执行模型提供的代码或组件       |
| 业务处理器 | 根据已注册 `formKind` 校验值、检查资源归属并执行领域写入           |

表单实例绑定当前用户、当前会话和一次聊天运行。用户不能通过客户端改写 `formKind`、字段权限、业务资源归属或提交目标。

## 动态表单协议草案

助手工具生成的安全表单对象：

```json
{
  "formId": "uuid",
  "formKind": "purchase_recipient",
  "title": "补充购买信息",
  "description": "请填写下单所需信息",
  "fields": [
    {
      "key": "recipient.name",
      "label": "收件人",
      "type": "text",
      "required": true,
      "value": null,
      "placeholder": null,
      "options": null
    }
  ],
  "submitLabel": "确认提交",
  "status": "open",
  "expiresAt": "2026-11-14T00:00:00.000Z"
}
```

### 字段规则

- `key` 是服务端注册的业务字段标识，不是任意数据库列名。
- `type` 首版只允许 `text`、`textarea`、`tel`、`number`、`select`、`checkbox`。
- `label`、`placeholder`、`description` 是纯文本，服务端限制长度并拒绝控制字符。
- `required` 由服务端结合 `formKind` 再确认，模型不能通过它绕过业务必填规则。
- `options` 仅用于 `select`，每项为服务端允许的稳定值与公开标签；不能由模型写入价格、库存、权限或身份字段。
- `value` 仅可作为服务端已知的非敏感初始值；姓名、手机号、详细地址等敏感值默认不回填到模型生成的表单定义中。
- 字段顺序由服务端保留，重复 `key`、未知类型、未知字段和过大定义全部拒绝。

### 首版字段白名单

| `formKind`           | 允许字段                                                                      |
| -------------------- | ----------------------------------------------------------------------------- |
| `purchase_recipient` | `skuId`、`quantity`、`recipient.name`、`recipient.phone`、`recipient.address` |

后续业务必须新增注册表项和对应处理器，不允许通过通用表单接口临时声明任意提交目标。

## 事件与提交

### SSE

- `form`：发送服务端校验后的表单定义，仅当前流有效；不写入普通 assistant 展示正文。
- `form-result`：提交确认后的安全结果引用，可包含 `formId`、状态、业务资源引用和公开 issues，但不包含敏感字段原值。
- `done`：沿用现有语义，仍表示聊天消息保存完成，不代表业务提交成功。

表单事件必须经过当前账号、会话和运行绑定。断流、切换会话或账号时，前端丢弃不属于当前页面上下文的事件。

### 提交

用户点击确认后，前端提交：

```json
{
  "formId": "uuid",
  "revision": 1,
  "values": {
    "recipient.name": "张三",
    "recipient.phone": "13800000000",
    "recipient.address": "示例地址",
    "quantity": 1
  }
}
```

服务端根据已保存的表单实例读取 `formKind`、字段白名单、当前用户和会话，不信任客户端重新提交的字段定义。提交成功后表单进入 `submitted`，相同 `formId` 和 `revision` 的重试返回同一结果；字段修改需要生成新 revision。

## 数据和隐私

- 表单定义可以绑定临时表单实例，但不把模型原始工具参数直接保存到公开聊天历史。
- 用户填写值只进入对应业务处理器和必要的业务持久化；不进入通用 tool activity、模型上下文、长期记忆或普通日志。
- 购买表单的收货信息仍遵守聊天购买和地址簿契约：只能更新当前本人购买草稿，正式下单仍由用户按钮执行。
- 服务端提交前必须重新校验表单未过期、版本未冲突、资源仍属于当前用户且业务状态允许写入。
- 表单提交失败时保留前端本地值，返回可公开的字段错误或业务冲突；不返回 SQL、内部异常、对象存储键或凭据。

## 模块边界

- `chat-records`：负责表单 SSE 事件、当前 assistant 展示绑定和会话归属。
- `chat-dynamic-form`：负责动态表单 schema、表单实例生命周期、提交幂等和处理器注册表。
- `chat-purchase`、`user-addresses` 等业务模块：提供领域处理器和公开端口，不暴露 Entity/Repository。
- `apps/web`：负责字段控件注册表、可访问表单卡片、输入状态和提交反馈。
- `llm`：只调用工具，不依赖前端组件或数据库 Entity。

## 非目标

- 不实现任意低代码页面编辑器。
- 不允许模型生成 Vue/HTML/JavaScript/CSS 并在浏览器执行。
- 不提供通用任意 API 代理、任意数据库字段写入或任意 webhook。
- 不让表单确认替代订单确认、支付、取消或确认收货按钮。
- 首版不支持文件上传、富文本、嵌套数组、条件脚本和自定义正则表达式。

## 待确认项

- 提交成功后是否同时向当前聊天追加一条结构化结果消息，还是只在表单卡片内显示结果。
- 表单实例是否需要跨页面刷新恢复；建议首版支持当前会话恢复，但不跨账号复用。
- 首版是否需要允许一个表单同时收集多个业务模块字段；建议先限制为一个 `formKind` 一个处理器。

## 验收清单

- [ ] 助手只能生成注册表允许的 `formKind` 和字段。
- [ ] 表单定义经服务端严格校验后才通过 SSE 发送。
- [ ] 前端未知字段类型、未知选项和损坏 JSON 安全降级。
- [ ] 用户确认前不写入业务资源；用户确认后由服务端业务处理器写入。
- [ ] 表单提交校验用户、会话、版本、过期时间和幂等。
- [ ] 敏感填写值不进入模型、trace、activity、历史公开展示和长期记忆。
- [ ] 购买表单不能创建正式订单，仍需显式确认下单。
- [ ] 购买草稿缺收件信息时先查询地址簿；非空显示地址选择卡，空列表才生成动态表单。
- [ ] 默认地址只作为卡片标记，不能自动选中或写入草稿。
- [ ] 断流、重复提交、切换会话和账号切换不会串写表单值。
