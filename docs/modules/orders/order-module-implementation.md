## 实施目标与非目标

按已批准契约和技术方案交付后端订单闭环：规格查询、多 SKU 下单、模拟支付、本人取消、订单查询、管理员整单发货、本人确认收货、超时关闭及商品目录库存协作。

不实施前端订单页面、聊天下单、真实支付、购物车、退款/退货/换货、物流轨迹或自动确认收货。不新增运行时依赖或测试框架，不执行会清空开发/共享数据库的命令。

## 开发前检查

主代理在启动子代理前：

1. 确认本实施文档已获用户明确确认；检查 `git status`，保留既有未提交改动。
2. 重读 `AGENTS.md`、订单 PRD/设计/契约/技术文档及商品目录契约；若接口、权限、状态或持久化规则发生变化，返回最早受影响的审批阶段。
3. 核对 `pnpm`、Node、API 包脚本、Nest/MikroORM/Zod 当前版本和现有 API 参数校验模式。
4. 与子代理书面固定 `ProductCatalogOrderPort`、订单应用服务公开入口、目录导入编排输入/输出及数据库锁序。不得让多个代理各自设计公共端口。
5. 确认 PostgreSQL 集成测试目标是独立、可丢弃的测试数据库，明确连接配置和启动方式；禁止使用 `migration:fresh` 指向常规本地库、共享库或生产库。
6. 为每个代理建立独占文件清单。子代理不得改写其他代理所有的文件；公共接线及根级文件由主代理维护。

## 子代理分工与文件所有权

所有子代理必须阅读 `AGENTS.md` 以及本业务 PRD、设计、CRUD 契约和技术文档。除任务指定文件外不得编辑其他路径；不得自行修改契约或已确认文档。新增必要代码注释使用中文。完成时按本文件“子代理完成报告”提交结果。

### 子代理 A：订单领域与 HTTP API

**所有权：**

- `apps/api/src/orders/` 下生产代码：Entity、DTO/Schema、Controller、Service、Mapper、Module 和公开导出。
- 不拥有 `orders/spec/`、Migration、`AppModule`、`ProductCatalogModule`、导入 CLI 或 Seeder。

**任务：**

- 实现订单状态流转、订单快照、金额计算、同用户幂等、本人/管理员查询、超时动作语义和响应白名单。
- 使用已固定的商品公开端口；不得导入商品私有 Entity、Repository 或 DTO。
- 每个 Body、Query、Param 使用所属 DTO 的 Zod strict schema 和现有 `StandardSchemaValidationPipe`。
- 复用既有 JWT、当前用户和角色授权能力；不新增认证或校验基础设施。
- 所有涉及库存的事务遵循 SKU UUID 升序、再订单 UUID 升序的锁序，并在锁内重新验证状态。

**交付验收：**

- 生产代码可由主代理集成；无跨模块私有导入；异常和投影符合契约。
- 报告修改文件、运行命令/结果、未解决风险及越界修改。

### 子代理 B：商品规格与库存公开能力

**所有权：**

- `apps/api/src/product-catalog/` 下生产代码：规格查询、库存公开端口、可售状态查询及供编排层使用的目录事务能力。
- 不拥有 `product-catalog/spec/`、订单模块、协调模块、Migration、根 AppModule、导入 CLI 或 Seeder。

**任务：**

- 提供不泄漏 Entity/Repository 的规格投影和事务内库存端口。
- 统一商品搜索、SKU 规格响应和下单校验的可售库存判断。
- 允许订单服务通过事务 EntityManager 加入同一事务；端口本身不得开启、提交或回滚调用方事务。
- 目录写入实现需能由订单目录协调器组合调用，不得直接导入或更新订单 Entity。

**交付验收：**

- 所有库存写能力使用指定锁序，基于锁内的实物库存与有效预占汇总做校验。
- 商品目录现有响应兼容性与聊天快照保持不变，除契约批准的 `inStock` 语义调整外不扩展聊天下单能力。
- 报告修改文件、运行命令/结果、未解决风险及越界修改。

**所有权：**

**交付验收：**

## 主代理所有权与集成职责

主代理独占以下公共和跨模块文件：

- `apps/api/src/app.module.ts`
- `apps/api/src/order-catalog-coordination/**`（协调模块及目录导入事务编排）
- `apps/api/src/database/migrations/Migration<timestamp>.ts`
- `apps/api/src/scripts/import-product-catalog.ts`
- `apps/api/src/database/seeders/ProductCatalogTestSeeder.ts` 及必要的 Seeder 注册
- `apps/api/src/mikro-orm.config.ts`（仅当确有必要且经契约/配置规则允许）
- `apps/api/package.json`、pnpm lockfile、CI/根配置及新增运行环境配置
- 非订单模块的公共契约/技术文档更新

主代理负责：

- 先固定并维护端口签名，协调 A、B 实现对齐。
- 实现目录导入与待支付订单关闭的单事务编排，避免模块循环依赖；改造 CLI 与测试 Seeder，使其不再绕过库存保护。
- 维护 Entity/Migration 注册和根模块接线；审查 Migration 生成 SQL、外键、索引、金额精度和回滚行为。
- 集成子代理工作，解决 API 类型和事务边界冲突，不覆盖或回滚用户已有修改。
- 检查任何订单相关导入、查询、推荐和 Seeder 路径是否仍使用旧的 `stock > 0` 口径。
- 最终执行自动化验证、隔离数据库迁移验证和 HTTP Smoke Test，并记录实际结果。

## 实施顺序与结果

### 阶段 0：确认与公共契约

- 用户确认本实施文档。
- 主代理复查工作区状态、测试数据库隔离和当前文件归属。
- 主代理先定义端口类型、交易 EntityManager 传递约定、异常语义、状态枚举、金额类型、分页响应和 Mapper 投影边界。
- A、B、C 阅读冻结后的公共接口说明；若技术文档与实际依赖不兼容，停止并回到相应审批阶段更新文档。

结果：已确认并冻结订单服务、商品库存端口、目录编排服务的公开边界。

### 阶段 1：并行模块实现

- A 实现订单领域与 HTTP 生产代码。
- B 实现商品规格与库存端口生产代码。
- C 按同一冻结契约编写 Schema/Service/HTTP 测试，并准备需要 PostgreSQL 的集成测试。
- 三方只修改其所有权范围；每项跨模块接口变动先交主代理裁定并同步其他代理，不以局部方便改变已批准业务规则。

结果：订单、商品目录库存能力和测试按文件所有权并行实现；主代理负责协调器、Migration、Seeder/CLI 及根模块接线。

### 阶段 2：主代理事务编排与数据库接线

- 审阅 A/B 的公开边界和统一锁序后，由主代理实现 `OrderCatalogCoordinationModule`。
- 在 Migration 中加入订单表、明细表、幂等表、外键、约束和索引；审查生成 SQL 与金额上界。
- 更新 MikroORM 实体发现/注册（仅当当前配置不自动发现新实体时），并接入 `AppModule`。
- 改造目录导入 CLI 和测试 Seeder，使预检、SKU 锁、下架订单关闭、库存校验、商品 upsert 在同一个事务内完成。
- 在隔离 PostgreSQL 验证全新安装和当前结构升级；不运行清库命令验证已有常规数据库。

结果：新增订单表、明细表、幂等表及预占视图；在隔离库应用完整 Migration 链。常规 `clothes_guide` 数据库未执行迁移。

### 阶段 3：集成修正与全量测试

- 将子代理分支/工作集成到共享工作区，先审查文件差异，再解决类型、依赖和边界问题。
- 执行单元、HTTP、PostgreSQL 并发和迁移测试；不得只因 unit tests 通过就宣称库存一致性已验证。
- 对关键竞争失败逐一核对：库存超卖、重复预占/释放/扣减、目录导入部分提交、旧请求覆盖新状态和幂等误复用。
- 确认错误响应、日志、管理投影、本人投影和下单详情没有暴露未授权个人数据。

结果：真实 PostgreSQL 测试发现并修复 SKU 数组绑定、实体写入顺序、目录锁查询排序及 upsert 主键保留问题。

### 阶段 4：Smoke Test 与交付

- 使用仅用于测试的账号、商品和隔离数据库，验证规格查询 -> 多 SKU 下单 -> 模拟支付 -> 管理员整单发货 -> 用户确认收货。
- 验证取消、支付超时、商品下架、缺货、重复请求、管理员越权及用户间隔离路径。
- Smoke Test 标明支付为模拟，不配置真实支付服务；测试数据和访问方式不得触及生产系统。
- 主代理记录文档/代码变更、子代理报告、配置、Migration 审核、验证命令和未解决风险。

结果：隔离 PostgreSQL 验证并发下单/幂等、多 SKU 完整履约、SKU 行锁、导入失败整体回滚和下架整单释放。真实支付未接入。

## 剩余风险与停止条件

- 若 `ProductCatalogOrderPort` 无法在不暴露商品 Entity 的条件下加入调用方事务，暂停商品/订单实现，先更新并重新审批技术方案。
- 若商品导入在获取 SKU 锁后发现受影响订单/SKU 集合变化，回滚当前事务并重新构造完整锁集合；不得在持有订单锁后补锁 SKU。
- 若账号删除、订单与 SKU 外键策略、导入覆盖语义或已批准 API 字段需要改变，暂停实现，更新最早受影响的设计/契约并重新审批。
- 后续部署环境仍需按环境计划执行增量 Migration，并确认运行配置及数据库备份/回滚安排。
- 若需要新运行依赖、支付能力、额外表/API、生产配置或扩大到前端/LLM，先提交提案并等待用户确认。
- 任意时刻发现工作区用户改动与本任务文件冲突时，保留原改动并先报告，不自行覆盖或回滚。
