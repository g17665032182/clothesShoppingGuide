# 用户偏好与用户记忆完整拆分设计

## 状态与上下文

- 状态：已确认，已实施并完成受控验收。
- 最后更新：2026-11-04。
- 需求来源：用户要求后端区分用户偏好和用户记忆，并补充“所有的都拆开”。
- 所属应用：`apps/api`；涉及接口和开关的前端调用需要同步适配。
- 当前阶段：设计、契约、技术与实施文档均已确认；代码、迁移及验证结果见实施文档的交付记录。
- 契约：[用户偏好](../../contracts/user-preferences-crud-contract.md)、[用户记忆](../../contracts/user-memory-crud-contract.md)。

本版替代“只拆代码职责、保留共用开关与任务”的上一版。2026-11-04 用户回复“确认”，批准本版完整拆分范围，包括路由、数据迁移、独立模型调用和前端必要适配。

## 需求初稿

目标是让维护者可以独立开发、测试和排查两类业务，让登录用户可以独立控制两类信息的形成与使用。

| 概念     | 含义                                 | 用户操作                                       |
| -------- | ------------------------------------ | ---------------------------------------------- |
| 用户偏好 | 结构化服装与购物信息                 | 管理尺码、风格、颜色、预算，独立控制提取与注入 |
| 用户记忆 | 每位用户的一份 Markdown 长期记忆文档 | 查看、编辑、清空文档，独立控制提取与注入       |
| 聊天     | 两类能力的调用方                     | 分别读取上下文，分别登记提取任务               |

普通用户只能管理自己的资源；管理员和客服不因拆分获得跨用户读取权限。游客不建立长期偏好或记忆。

### 当前问题

- 同一个 Controller 管偏好、设置和文档。
- `UserMemoryService` 实际管理结构化偏好，同时修改共用设置及任务。
- 同一个提取器、模型响应和任务记录承载两类更新。
- 同一个读取器查询偏好并匹配 Markdown 段落。
- 删除全部偏好会取消共用未完成任务，影响尚未执行的 Markdown 更新。
- 共用提取器先读取文档，存储失败可能阻止偏好提取。
- 实体、DTO、类型和测试的 memory 命名难以区分两类业务。

这些是代码调查结果，不代表本次拆分已实施。

## 完整拆分范围

| 层次     | 用户偏好                              | 用户记忆                                 |
| -------- | ------------------------------------- | ---------------------------------------- |
| 模块     | `user-preferences`                    | `user-memory`                            |
| 接口     | `/api/preferences` 及偏好设置         | `/api/memories/document` 及记忆设置      |
| 领域规则 | 类别校验、去重、主偏好、多值合并      | 文档安全、revision、补丁、对象完整性     |
| 数据     | 偏好、设置、任务和操作结果            | 文档状态、设置、任务、操作结果和对象清理 |
| 开关     | 独立 enabled                          | 独立 enabled                             |
| 提取     | 独立提示、schema、模型调用和结果应用  | 独立提示、schema、模型调用和补丁应用     |
| 调度     | 独立领取、重试、恢复和错误记录        | 独立领取、重试、恢复和错误记录           |
| 读取     | 只生成偏好上下文                      | 只生成相关 Markdown 上下文               |
| 删除     | 只处理偏好及偏好任务                  | 只处理文档及记忆任务                     |
| 测试     | 独立 schema、Service、HTTP 和任务测试 | 独立 schema、Service、HTTP 和任务测试    |

认证、数据库连接、日志和 LLM 公共生成端口仍复用现有基础设施；不得为拆分复制 JWT、连接池或模型客户端。业务设置、任务记录、提示和领域状态全部分离。

不新增向量检索、第三类个性化模块、任务队列产品或模型供应商。

## 模块边界

### 用户偏好

`apps/api/src/user-preferences/` 独立维护 Controller、DTO/schema、响应映射、Entity、设置、提取器、调度器、任务及测试，负责：

- 偏好 CRUD、分页、值校验、主偏好、多值合并与去重。
- 结构化候选应用、操作幂等、来源会话状态。
- 独立偏好上下文、开关和删除生命周期。

不得注入文档服务或读写文档状态、七牛对象、记忆任务与文档 generation。

### 用户记忆

`apps/api/src/user-memory/` 独立维护同类职责目录，负责：

- 文档读取、编辑、清空、revision、generation 及精确补丁。
- 记忆设置、独立提取及任务幂等。
- 七牛存储、摘要、延迟清理及相关 Markdown 上下文。

不得维护偏好类别、主偏好或多值合并，不依赖偏好模块。

### 聊天接入

- 分别调用两个模块的公开入口，不直接访问私有 Entity、Repository、DTO 或内部任务实现。
- 在聊天持久化事务中分别登记两类任务，任务去重和执行状态各自维护。
- 不保留统一业务开关、统一任务表、统一提取响应或包办两类业务的提取器。
- 两类上下文分别读取；一边失败时保留另一边结果并继续普通聊天。
- 聊天组合已生成的上下文，优先级保持当前消息 > 结构化偏好 > Markdown 记忆 > 系统默认规则，总预算为 512 token。
- 一边关闭或无结果时，另一边仍可独立使用可用预算。
- 来源会话删除通知直接送达需要处理的领域，不通过记忆模块间接修改偏好。

复用本地已有 Nest、MikroORM、Zod 和模型生成端口，不引入新框架。公开入口、依赖注入、事务参数和锁顺序在技术阶段确定。

## 开关与失败隔离

| 偏好开关 | 记忆开关 | 行为                           |
| -------- | -------- | ------------------------------ |
| 开       | 开       | 分别提取、分别生成上下文       |
| 开       | 关       | 仅提取和注入偏好               |
| 关       | 开       | 仅提取和注入记忆               |
| 关       | 关       | 不提取、不注入，普通聊天仍可用 |

- 开关默认开启；关闭不删除历史数据，不禁止手动管理。
- 每个领域在任务开始及提交前检查自己的开关，关闭后旧结果不能继续落库。
- 一边模型或存储失败仅重试该领域任务，不改变另一边状态。
- 两边开启时可能产生两次独立模型调用，需要接受相应成本和限流变化。
- 两边任务恢复、并发控制、停止行为和日志分别维护。

## 已确认 API

| 操作               | 方法及路径                              |
| ------------------ | --------------------------------------- |
| 偏好分页、创建     | `GET/POST /api/preferences`             |
| 更新、删除单条偏好 | `PATCH/DELETE /api/preferences/:id`     |
| 删除全部偏好       | `DELETE /api/preferences`               |
| 偏好设置           | `GET/PATCH /api/preferences/settings`   |
| 文档读写及清空     | `GET/PUT/DELETE /api/memories/document` |
| 记忆设置           | `GET/PATCH /api/memories/settings`      |

旧结构化 `/api/memories` 与 `/api/memories/:id` 路由移除，不留混淆名称的兼容别名。偏好分页中的 settings 只代表偏好开关。原 `/api/memories/settings` 改为只控制记忆，需同步升级调用方。

两类设置响应可以具有相同字段形状，但类型、接口、数据和语义独立。请求继续使用 Zod 与 Nest 标准校验 Pipe；权限、偏好值约束、文档大小和 revision 冲突规则保持。

## 已确认数据与迁移范围

| 数据           | 目标归属及表                                                                |
| -------------- | --------------------------------------------------------------------------- |
| 结构化偏好     | `user-preferences`：`user_preferences`                                      |
| 偏好设置       | `user-preferences`：`user_preference_settings`                              |
| 偏好任务及结果 | `user-preferences`：`user_preference_tasks`、`user_preference_task_results` |
| 文档元数据     | `user-memory`：`user_memory_document_states`                                |
| 记忆设置       | `user-memory`：`user_memory_settings`                                       |
| 记忆任务及结果 | `user-memory`：`user_memory_tasks`、`user_memory_document_task_results`     |
| 对象回收       | `user-memory`：`user_memory_document_cleanups`                              |

- 原偏好数据和结构化操作结果迁入偏好命名，保留记录 ID、值、归属、来源、删除状态和幂等关联。
- 原共用开关按原值初始化两类设置，原值 false 不得变为开启。
- 原共用任务转换为两类独立任务；保留历史成功及部分成功结果，不能因转换重新提取已完成操作。
- 转换时暂停旧调度和旧服务写入。processing、attempts、锁及部分成功结果如何恢复由技术文档明确，不默认丢弃任务。
- 新偏好任务不带文档 generation；记忆任务只管理记忆操作结果。
- 七牛对象、文档 revision、摘要及清理记录不因拆分改变。
- 需要新增并审阅 Migration，不改写已执行的历史迁移。

本地执行迁移遵循用户已确认的 `pnpm migration:fresh`，会清空本地数据并自动 Seed；当前文档阶段不执行数据库操作。需要保留数据的环境仍须设计并验证数据转换，不能用本地重建替代兼容性审查。

## 删除与生命周期

- 删除单条偏好沿用逻辑删除，不影响记忆。
- 删除全部偏好只取消偏好任务及回写，不取消记忆任务或修改正文。
- 清空文档只修改文档状态、隔离旧记忆任务并登记对象回收。
- 清空/全部删除与本领域在途任务必须互斥，接口返回后旧任务不能恢复内容。
- 来源会话删除不等同于清空长期数据，沿用原有来源处理规则。
- 未来账号物理删除由两边分别清理自身资源，本次不把逻辑禁用接口扩展为物理删除。

## 前端必要适配

最初需求限定后端，但完整拆分改变接口与开关，以下必要联动已随本设计确认：

- API 模块和类型分别表达 preferences 与 memories，偏好记录不再命名为 MemoryRecord。
- 保留现有两个视图，各自提供独立开关和状态。
- 偏好调用新接口，文档独立加载和修改记忆设置。
- 两边加载、错误、保存、取消及过期响应保护独立。
- 不新增独立导航页，不做无关视觉重设计。

## 已确认决策与技术风险

以下具体方案已随本文确认：

1. 偏好改用 `/api/preferences`，移除旧结构化路由，调用方同步升级。
2. 设置、任务及模型调用独立，接受双开时调用量增加。
3. 表名按领域调整，原设置原值复制，旧任务及结果分别转换。
4. 包含前端 API、类型及两个开关的必要适配，保留现有页面组织。

旧任务转换与恢复细节留在技术阶段；若无法保持幂等和清空语义，回到设计确认替代方案。
