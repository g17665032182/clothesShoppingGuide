# 聊天通用卡片展示设计文档

## 状态与上下文

- 状态：商品/订单卡片及 2026-11-13 确认的下单地址选择卡均已实施；登录态浏览器验收未执行。
- 业务目的：为聊天中的商品、订单等结构化内容提供统一卡片协议，并由前端按卡片名称选择对应模板。
- 所属应用：`apps/web`、`apps/api`。
- 关联模块：`chat-records`、`llm`、`product-catalog`、`orders`、`user-addresses`、`chat-purchase`。
- 最后更新：2026-11-13。
- 关联契约：[聊天卡片展示 CRUD 契约](../../contracts/chat-card-display-crud-contract.md)。

## 目标与范围

目标流程：

1. 助手需要展示结构化商品或订单列表时，调用统一的前端展示工具。
2. 展示工具返回统一卡片 JSON，使用 `type: "card"` 标记卡片内容，并通过 `name` 选择展示模板。
3. MarkdownRenderer 解析该 JSON；卡片模板分发器按 `name` 渲染商品、订单等组件。
4. 未识别或不符合对应模板结构的数据不作为卡片渲染。

已实现模板为商品列表 `product`、订单列表 `order` 和下单地址选择 `address_selection`。地址卡只保存当前购买草稿的安全引用，由前端读取本人地址 API 并让用户明确选择。订单卡只读；商品卡沿用现有商品卡展示字段和既有交互事件，不把卡片协议作为新的操作授权入口。

本设计不改变商品搜索筛选、本人订单查询、订单状态流转和现有购买/取消确认规则。现有业务工具继续负责获取真实业务数据，卡片展示协议只负责承载与渲染经允许公开的数据。

## 用户与权限

| 角色           | 能力                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| 已登录聊天用户 | 查看绑定到本人聊天回复的卡片内容                                           |
| 聊天助手       | 请求展示已获准提供给当前回复的结构化内容；不能扩展数据权限或执行订单写操作 |
| 前端渲染器     | 校验协议标记并选择注册的卡片模板；不把未知 JSON 当作可信业务对象           |

卡片数据不能扩大原有用户及会话权限。商品字段遵循商品目录公开字段白名单；订单字段遵循本人订单及聊天展示白名单，不含收件人、手机号、详细地址、物流单号、支付凭据或内部用户信息。

## 卡片协议草案

逻辑结构暂定为：

```json
{
  "type": "card",
  "name": "product",
  "data": {}
}
```

- `type` 为固定字面值 `card`。
- `name` 是有限注册表中的模板标识，已实现 `product`、`order`、`address_selection`。
- `data` 按 `name` 使用独立结构校验；不允许使用通用任意对象直接驱动模板。
- 未知 `name`、非法 JSON、未知字段或超出数据上限时，不渲染卡片，也不显示为可执行业务控件。
- 每张卡片最多包含 5 个条目；卡片与现有展示数据共用 16 KiB `publicDisplay` 字节预算，超限时拒绝新增卡片且不截断业务字段。

地址选择卡数据只含：

```json
{
  "draftId": "uuid",
  "draftVersion": 1
}
```

该卡不携带地址 ID 列表、收件人姓名、手机号、地址文本或用户自定义标签。前端使用当前认证身份读取本人地址列表，在组件内存中展示；默认地址可以有标记，但不得预选或自动写入。用户点击某地址后，前端通过认证的购买地址选择操作提交地址 ID 与草稿版本；服务端校验用户、地址及草稿归属/版本，再更新草稿。不得将点击动作转成普通聊天文本等待模型执行。

助手通过 `display_chat_card` 工具请求展示卡片。工具只接收模板标识及本轮领域查询结果的引用；服务端根据本轮已登记的安全来源生成卡片数据，不接受模型提交的任意业务字段。

展示工具返回的 JSON 由服务端校验后，作为受控结构化数据交给聊天 Markdown 展示层，由展示层按协议和模板注册表分发。普通 assistant 正文中的 JSON 不自动作为卡片协议解析。

## 数据来源与安全边界

- 商品目录和订单领域工具继续作为业务事实来源；卡片不得由模型凭空编造商品价格、库存、订单状态或订单标识。
- 服务端须验证公开字段并将卡片绑定到对应 assistant 消息；实时流与历史恢复使用同一白名单规则。
- 普通 assistant Markdown 中偶然出现的 JSON 不自动视为可信卡片来源。
- 订单卡片若包含支付、取消、确认收货等动作，动作仍需沿用现有用户显式确认和本人 API 授权；不能因为卡片 `name` 或 JSON 字段而获得写权限。
- 卡片数据通过独立 `card` SSE 事件进入 Markdown 展示层；历史数据只从绑定到对应 assistant 消息的 `publicDisplay.cards` 恢复。不从任意模型正文中搜寻 JSON。
- 地址选择卡只能由当前本人购买草稿和服务端验证过的非空地址列表来源生成。历史恢复时重新读取当前草稿和地址列表；草稿不可编辑、会话/账号不匹配或地址加载失败时禁用选择并允许安全重试。
- 地址详情由前端本人 API 临时读取，不写入 `publicDisplay`、Pinia 持久化、localStorage、模型上下文、trace、activity 或应用日志。
- 展示工具不能凭模型提供的商品价格、库存或订单状态构造卡片；须引用并校验服务端已取得的领域数据。
- 卡片模板分发使用本地明确注册表，未知 `name` 不动态加载组件。

## 模块边界

- `product-catalog`、`orders`、`user-addresses` 与 `chat-purchase` 继续拥有各自业务数据、查询和状态规则。
- `llm` 负责模型与现有领域工具调用，不直接引用前端组件或业务 Entity。
- `chat-records` 负责会话归属、公开投影、assistant 消息绑定、历史恢复和流式展示事件。
- `apps/web` 的 Markdown 展示层负责协议解析；卡片模板分发器负责按 `name` 映射到有类型的卡片组件。
- 前端卡片组件不直接依赖后端 Entity、Repository 或内部 DTO；跨模块使用现有公开接口与 API 类型。

## 兼容性与非目标

- 已保存的普通聊天正文、旧消息和未知卡片名称必须安全降级，不能破坏 Markdown 阅读。
- 现有 `productResults`、`orderCancellationCandidates` 和 `purchase` 展示字段继续工作，不迁移或删除；新卡片与它们并存。
- 不新增商品查询、订单查询或订单写接口作为展示协议的副作用。
- 不从工具 trace、模型历史或客户端提交的历史正文直接恢复可操作卡片。
- 不因本功能新增数据库 Entity 或 Migration；如技术评估证明必须改变数据结构，应回到本阶段确认。
