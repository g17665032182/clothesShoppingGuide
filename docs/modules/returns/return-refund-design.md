# 退货退款设计文档

## 状态与上下文

- 状态：已确认。
- 业务目的：让用户既可在聊天中经助手协助创建退货退款申请，也可直接从本人订单页申请；用户在订单页提交和跟进，管理员在本站处理审核与退款登记。
- 所属应用：`apps/api`、`apps/web`；订单与售后记录由订单领域负责，聊天仅提供受限申请创建能力。
- 最后更新：2026-11-20。
- 关联契约：[退货退款 CRUD 契约](../../contracts/return-refund-crud-contract.md)。

## 范围

### 包含

- 助手查询当前用户本人订单及可申请商品摘要，用户选定订单中的一个或多个商品及数量。
- 助手询问并记录用户自由描述的退货原因；创建前展示订单、商品、数量、金额和原因，必须再次获得用户明确确认。
- 大模型必须通过已注册的退货退款工具才能创建申请；工具在确认后创建“待用户提交”申请。用户在订单页补充/修改申请资料并提交，凭证上传可选且可后补。
- 用户也可不经大模型，直接从本人订单页选择商品和数量、填写原因并提交退货退款申请；该入口创建的申请直接进入待审核状态。
- 规则初筛：订单为 `completed` 且当前北京时间自然日仍在确认收货日起第 7 天内，标记为规则内申请；确认收货当天算第 1 天，第 7 天 23:59:59.999 截止。超期或订单未完成/状态无法判定的申请不拒绝，标记为待人工审核。
- 用户在订单页查看申请状态、上传可选凭证；审核通过后填写退货承运商和物流单号。
- 管理员在本站后台查看和审核申请、拒绝申请、确认退货收货与验货，并登记退款处理中/退款完成。
- 退款金额使用订单明细快照单价乘申请数量，由服务端计算并固定，管理员不可修改。
- 同一订单最多存在一条未结束申请；申请结束后可重新申请，但累计已登记退款数量不得超过购买数量。
- 用户仅可在“待用户提交”或“待审核”阶段取消申请。

### 明确不包含

- 真实支付渠道退款、银行或第三方资金操作；“已退款”仅代表管理员在本站登记退款完成。
- 商品级可退资格配置、真实店铺政策或法律资格判断、商家售后 API、自动退款。
- 换货、部分退款金额调整、退款运费/优惠分摊、管理员代替用户填写或提交申请。
- 助手代用户上传凭证、填写物流信息或推进审核状态。

## 用户与流程

1. 用户可在聊天中让助手协助创建，也可直接从本人订单页发起申请。
2. 聊天路径中，用户选择订单商品及退货数量、提供退货原因；助手展示将要创建的申请摘要并询问最终确认。用户确认后，工具创建“待用户提交”申请；该动作不代表正式提交给管理员审核。
3. 用户在订单页检查/补充助手创建的申请并提交；订单页独立路径则由用户填写相同必要信息并直接提交。两种路径正式提交后均进入审核流程。
4. 系统按订单状态和 `completedAt` 做规则初筛：确认收货当天算第 1 天，第 7 个北京时间自然日结束前为常规待审核；之后、未完成或无法判定时设置待人工审核标记，不自动拒绝。
5. 管理员审核；通过后用户寄回商品，并在订单页填写一组承运商和物流单号，申请进入“用户已寄回”。
6. 管理员确认收到并完成验货，推进至“待收货验货”之后的退款处理；管理员登记“退款处理中”，退款完成后登记“已退款”。
7. 管理员也可拒绝申请并记录原因。用户可在允许阶段取消。

## 状态

```text
待用户提交 -> 待审核 -> 已通过待寄回 -> 用户已寄回
           -> 待收货验货 -> 退款处理中 -> 已退款
                         -> 已拒绝
待用户提交 / 待审核 -> 已取消
```

规则初筛的“待人工审核”使用待审核状态及明确的人工审核标记/原因表达，不由模型自行做资格判断。状态字段、原因枚举和并发状态转换的具体存储方式留待技术阶段。

## API 与交互边界

- 所有用户售后资源绑定认证上下文中的当前用户；请求不接受 `userId`。
- 助手只能通过服务端已注册的退货退款工具查询本人订单、创建经用户确认的“待用户提交”申请；模型文本、前端推断或普通聊天内容不能创建记录。工具不能提交申请、同意/拒绝、填写物流、验货或登记退款。
- 用户订单页负责独立创建并提交申请，也负责查看、补充和提交助手创建的申请，取消允许范围内的申请、上传凭证、提交退货物流。
- 管理员后台复用既有管理员角色，在独立售后管理流程中审核及推进状态。
- HTTP 路由、分页参数、请求/响应 DTO 与错误码在技术阶段依据确认后的 CRUD 契约细化。

## 数据和行为

- 申请关联一笔本人订单及其中一个或多个订单明细；每项包括申请数量和订单快照单价。
- 申请金额为所有申请项“快照单价 × 数量”之和，不接受客户端或管理员改价。
- 订单商品与数量必须来自原订单明细；数量不得超过尚未登记退款完成的可申请数量。
- 同一订单只允许一条进行中的申请；并发创建必须由服务端原子约束，不能仅靠前端检查。
- 已完成退款的商品数量累计扣减可申请数量；拒绝或取消不扣减，已拒绝/取消申请的数量可重新申请。
- 申请创建、正式提交、状态变更和退款登记均保留必要审计信息；具体字段在技术阶段确定。
- 证据文件权限、大小/类型、保存与删除规则在技术阶段按现有私有文件安全边界设计；没有确认前不允许公开 URL 或模型访问文件。

## 模块边界

- 售后领域负责售后申请、状态流转、重复申请约束和管理员处理。
- 订单领域通过公开服务/Port 提供本人订单与明细快照读取，不向售后模块暴露私有 Repository/Entity。
- 聊天模块调用售后模块公开入口；工具用户身份和会话来自服务端认证/聊天上下文。
- Web 订单页只调用认证 API；聊天助手不能直接触发管理操作。
- 既有订单模拟支付状态不等于真实款项。售后模块不得宣称执行了实际退款。

## 待确认项

- “7 天”按 `Asia/Shanghai` 自然日计算，确认收货当天为第 1 天，第 7 天 23:59:59.999 截止；提交时使用服务端可信时钟判定。
- 订单状态变化与已创建售后申请之间的竞态处理、申请资料修改截止时机、审计保留期限待技术阶段细化。
- 凭证使用私有存储；只支持 JPG/PNG/WebP 图片和 MP4 视频，每申请最多 5 份，图片每份最大 10 MiB、视频每份最大 50 MiB。

## 验收清单

- [ ] 用户只能为本人订单创建、查看和操作售后申请。
- [ ] 助手创建前必须收集商品、数量、原因并取得明确确认；不确认不创建。
- [ ] 用户可从订单页独立创建并提交申请，无需启动聊天或调用模型。
- [ ] 创建后为“待用户提交”；用户提交后依据北京时间自然日规则标记常规审核或人工审核，不自动拒绝。
- [ ] 只允许订单明细中的有效数量；重复或并发申请不能超过未退款数量。
- [ ] 一笔订单最多一条进行中申请；结束后可重开且不会重复退款。
- [ ] 用户可选上传凭证；通过后物流信息必填。
- [ ] 管理员可审核、拒绝、确认收货验货并登记退款处理状态。
- [ ] “已退款”仅为本站状态记录，不触发真实支付/退款。
