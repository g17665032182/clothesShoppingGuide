## 范围冻结

### 必须交付

- `return-refund` API 领域模块、申请/明细/凭证/审计数据、增量 Migration、用户与管理员 API。
- 订单模块只读快照 Port，供售后校验本人订单及真实订单明细 ID。
- 聊天工具查询本人申请候选/商品行，并在用户明确确认后通过注册的 `create_return_refund_application` 写入待用户提交申请；没有工具调用不得产生申请。
- Trace、history、activity、自动记忆/摘要来源按技术文档做白名单与隔离。
- 用户订单页可独立创建并提交申请，也可补全助手创建的申请；可选凭证、允许阶段取消、通过后登记退货物流、查询申请状态。
- 管理员售后列表/详情、审核通过/拒绝、确认收到、验货后退款处理中和退款完成登记。
- 所有金额由订单快照服务端计算；禁止真实退款操作；同订单活动申请唯一、累计已退款数量上限和事务竞态保护。
- 更新对应契约、LLM 工具能力清单、开发速读/模块索引及 README 的相关入口/功能说明；更新实施文档实际交付与验证记录。

### 排除

- 真实支付/退款、第三方商家售后 API、换货、任意退款金额调整。
- 由模型直接调用订单或管理员 HTTP API、从聊天文本或历史 Markdown 解析可执行申请。
- 管理员商品编辑、订单状态编辑、跨用户聊天工具。
- 运行 `migration:fresh`，写入默认开发/生产数据库，安装额外依赖或部署外部环境。

## 实施默认值

以下实现边界采用当前首期默认值：

- 资格窗口按北京时间自然日计算，确认收货当天算第 1 天，第 7 天 23:59:59.999 截止且包含。
- 凭证支持 JPG/PNG/WebP 图片（每份最大 10 MiB）及 MP4 视频（每份最大 50 MiB），每申请最多 5 份；用户在待用户提交/待审核阶段可删除，私有存储且随申请记录保留。
- Qiniu 目标 bucket 是否允许售后模块复用现有 Qiniu 配置；若不允许，新增配置/密钥前重新确认部署范围。
- 聊天确认的产品安全级别：当前方案以用户在聊天明确确认后模型调用写工具为流程约束；若要求由服务端可验证的确认凭证，需变更设计加入用户显式 UI 确认，不可只靠提示词。

上线前核验 Qiniu 目标 Bucket/config 只使用授权的非生产验收环境；未确认生产存储配置前不得上传生产对象。

## 文件所有权与工作分组

按 API 售后领域、聊天工具与隐私、Web 用户/管理员界面拆分给子代理；主代理负责公共模块接线、跨模块集成、文档和最终验证。子代理文件所有权互斥，数据库、迁移与构建相关验证由主代理串行执行。

### A. 售后 API 与持久化

- API 子代理负责 `apps/api/src/return-refund/**`：Entity、DTO、Service、Port、Controller、存储适配器和测试。
- API 子代理负责售后增量 Migration；主代理维护 `apps/api/src/app.module.ts`、`apps/api/src/mikro-orm.config.ts`（如有必要）、订单模块接线及 `apps/api/src/orders/**` 的最小 Port 实现。
- 覆盖 schema、service、HTTP 权限/状态、附件、本模块 PostgreSQL 与 Migration 测试。

### B. 聊天工具与执行安全

- 聊天子代理负责 `apps/api/src/chat-records/tools/**` 中售后工具、`chat-records.service.ts` 的工具装配、`chat-records.module.ts` 的模块注册。
- 聊天子代理负责 `apps/api/src/chat-records/trace/**`、`history/**`、必要 DTO/schema/spec 与 `apps/api/src/llm/context/**` 的售后上下文。
- 只有注册工具能创建待用户提交申请；写工具严格按已确认用户和当前会话组装。对工具输入/输出执行 trace/history 安全投影；活动中不返回原因/参数/文件/物流信息。
- JSON/SSE 共用工具装配；工具查询与写入轮次都执行当前 detail-query 来源隔离。

### C. 用户订单页

- Web 子代理负责 API 类型与请求封装：`apps/web/src/api/modules/return-refund.ts`、`apps/web/src/api/types/return-refund.ts`。
- Web 子代理负责订单页面及组件：`apps/web/src/pages/account/orders/**`，保留已有用户界面工作；新增状态与异步请求必须遵守当前账号/会话切换保护。
- 支持订单页直申和助手草稿续办两种路径，但共享申请详情/状态显示；避免重复的独立订单读取逻辑。

### D. 管理员售后页

- Web 子代理负责新增 `apps/web/src/api/modules/admin-return-refunds.ts`、`apps/web/src/api/types/admin-return-refunds.ts`。
- Web 子代理负责新增 `apps/web/src/pages/admin-return-refunds/**`；只支持契约中的售后审核与状态动作，不扩展商品/普通订单管理权限。
- 更新管理员路由、侧边导航和授权守卫接线；访问控制仍由服务端角色校验最终决定。

### E. 文档与根级集成

- 主代理独占 `apps/api/src/app.module.ts`、`apps/web/src/router/index.ts`、共享菜单/导航注册、文档索引、README 和本实施记录。
- 文档将记录真实实现、实际运行验证及跳过/未执行项，不把计划或静态审阅表述为通过。

## 实施顺序

### 阶段 0：冻结输入与接口

- 核实用户确认的技术文档及上述开工门槛。
- 固定订单 Port 只读返回类型、售后 DTO schema、状态枚举、部分唯一索引、事务锁顺序、对象存储接口和聊天工具 trace 投影。
- 核对当前工作区差异，明确既有文件修改所有者；冲突文件不得覆盖。
- 退出条件：所有会影响规则、字段、权限、数据迁移或附件的未知项已经确认；否则暂停相应代码范围。

### 阶段 1：订单公开 Port 与售后领域

- 在订单模块提供最小只读本人订单/明细快照接口，返回稳定 `OrderItem.id`，不增加通用订单写 API。
- 新增售后模块、严格 DTO schema、Service、Entity 和 Migration；增加订单级活动申请唯一性、状态审计和商品数量/金额不变量。
- 实现用户直接申请、助手草稿提交、本人查询/取消/凭证/物流以及管理员专用状态动作。
- 先写单元与 schema 测试；确认隔离数据库与开关后运行 PostgreSQL 测试和 Migration 升级/回滚/再升级。
- 退出条件：领域不变量和权限规则通过单测；隔离库事务/迁移测试实际完成或明确列为阻塞缺口。

### 阶段 2：聊天工具与隐私集成

- 接入订单候选查询、申请商品查询和创建工具。所有写入只在模型调用注册工具后发生。
- 将 tool calling、本人 userId、conversationId、toolCallId 与幂等处理正确绑定；模型不得提供身份字段或用户确认结果之外的业务状态。
- 为工具请求/结果、trace/history/activity 和记忆/摘要来源添加严格安全投影。
- 更新运行时系统提示文本，要求助手先核实订单/商品/数量/原因、展示固定金额并等待用户明确确认，再调用写工具。
- 验证 JSON 和 SSE 两路，失败、重试、模型中断或伪造卡片均不产生/展示虚假成功。
- 退出条件：只有确认后的注册写工具能创建；原因文本、凭证信息、物流单号和收件资料不出现在 trace/activity。

### 阶段 3：用户订单页流程

- 在本人订单页增加申请入口与申请记录浏览，支持商品/数量选择、原因填写、金额摘要和显式提交。
- 助手创建的待用户提交申请进入相同详情界面；用户可提交或按规则取消。
- 支持配置图片/视频凭证的类型、数量、大小限制；凭证可选、私有上传、授权读取及删除。
- 审核通过后用户填写一组承运商/物流单号，服务端状态推进。
- 验证窄屏布局、加载/错误/未知状态、重复点击、账号切换和请求中断；不假称已有浏览器测试框架。

### 阶段 4：管理员处理界面

- 增加管理员售后分页列表、筛选、详情和凭证预览/下载。
- 提供通过、拒绝并说明原因、确认收到、验货后退款处理中、退款完成登记。
- 所有状态动作带版本号/并发保护；金额只读，清楚标记为本站登记，不存在实际退款 API。
- 验证普通用户的前后端访问均被拒绝，管理员只看到必要审核数据。

### 阶段 5：集成、文档和回归

- 更新 API/Web 模块接线、路由、导航、README、业务索引、工具能力清单和契约实现状态。
- 复查新增 Migration 的完整 SQL、向上/向下顺序、历史订单兼容和索引条件；禁止清库命令。
- 执行格式、类型检查、API 测试、API/Web build、仓库 `pnpm check` 和 `git diff --check`；共享 build 目录的命令串行运行。

- 更新实施记录，逐项标明通过、失败、跳过和未执行。

## 验收标准

- 助手申请必须调用专用注册工具；工具结果只代表已创建待用户补充申请，不宣称正式提交或已退款。
- 用户可独立从订单页申请；同订单活动申请唯一，终态后重开正确，累计已退款数量不超购买数量。
- `pending_review` 的常规/人工标记只由服务端状态、完成时间和时钟计算；超期/未完成/时间不明不自动拒绝。
- 用户身份与订单、订单项、申请、附件归属核验通过；管理员 API/UI 受角色控制。
- 订单快照金额不可由客户端、模型或管理员写入；审核期间价格变化不影响申请金额。
- 各状态只能按契约流转；重复/并发请求不造成重复申请、审计事件或退款数量。
- 凭证始终私有，下载要求认证并核验归属；敏感值不泄漏到聊天、trace、公开历史或日志。
- 不新增真实支付/退款路径或未确认的附件/时间规则。
- API/Web 自动化、隔离数据库、构建、界面 Smoke Test 各自单独报告，不互相替代。

## 风险与停止条件

- 资格使用服务端可信时钟与 `Asia/Shanghai` 自然日；不得用客户端时间或主机本地时区隐式替代。
- 附件必须校验文件签名与实际解码格式、严格限额并保持私有；不得以浏览器 MIME 为准或生成公开 URL。
- Qiniu 目标配置或 Bucket 未授权：不写入该存储；先改用经确认的隔离测试配置。
- 数据库唯一索引无法跨订单并发保证活动申请唯一：停止状态写入，不降级为仅应用层检查。
- 当前模型工具无法可靠隐藏申请原因或物流资料：停止聊天工具上线，不能仅靠提示词替代 trace/history 投影。
- 订单项主键、金额快照或状态与既有订单契约不一致：停止并回到设计/契约阶段，不猜测转换方式。
- Migration 测试没有具名隔离库、回滚可能影响默认数据库或 teardown 不清楚：不运行数据库操作并报告阻塞。
- 真实退款、换货、商家政策或第三方接口要求超出现有范围时：停止并重新走设计/契约审批。

## 实施结果

- 后端已新增售后申请、申请明细、事件与凭证 Entity、严格 Zod schema、用户/管理员 Controller、事务 Service、订单只读 Port、北京时间自然日资格策略及私有 Qiniu 凭证适配器。

- “已退款”仅表示管理员在本站登记；没有真实支付或资金退款调用。
