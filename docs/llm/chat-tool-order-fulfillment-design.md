# 对话本人订单履约摘要设计

## 状态与背景

- 状态：用户授权直接完成文档并实施；代码已完成，业务测试和运行验收暂缓。
- 日期：2026-11-17。
- 业务依据：[能力清单](./chat-tool-capability-inventory.md)。
- 行为依据：[履约摘要契约](../contracts/chat-tool-order-fulfillment-crud-contract.md)。

地址导航工具已完成。下一阶段针对“这笔订单发货了吗”提供精确订单号查询。仓库只有管理员登记的本地发货快照，没有承运商轨迹来源；因此本阶段提供本地履约状态，明确不代表实时物流。

现有 `list_my_orders` 已可回答列表级状态问题。本工具的增量是对一笔明确订单进行最小字段、独立只读查询，并在响应中固定声明来源及不支持实时轨迹；不重复新增订单列表、商品明细或管理页面。

## 用户流程与范围

1. 用户明确询问某笔本人订单的发货或履约情况。
2. 订单号明确时调用 `get_my_order_fulfillment`；只有“这个订单”等歧义表达时，先查询现有订单摘要或询问，不能猜测订单号。
3. 服务端绑定本人身份，精确查询该订单的状态、发货及完成时间。
4. 模型根据本地记录回答，明确无法查询实时物流。
5. 完整订单信息和后续操作继续由用户进入已有“我的订单”页面处理。

只包含读取；不新增承运商对接、轨迹、ETA、物流单号脱敏显示、卡片、导航事件、轮询或通知。不增加订单写能力，保持创建、支付、取消、发货及收货的原权限。

## 数据和权限决策

- 只返回已允许进入聊天的 `orderNo`、`status`、`shippedAt`、`completedAt`。
- 固定 `source: "local_order_record"` 和 `realtimeTrackingAvailable: false`，不伪装成物流服务响应。
- 首版连承运商名称和部分单号都不返回。承运商在当前模型中是管理员填写的自由文本，没有可安全作为公共枚举的现成来源。
- 身份来自当前认证聊天上下文，不接受模型指定用户。本人不存在和他人资源保持同一种安全错误。
- `pending_receipt` 只表示本站已登记发货；`completed` 只表示本站订单已完成，两者都不能用于推断承运商轨迹或签收事实。
- 不因“过期”执行写入或把本地状态自动改成关闭。查询只如实返回快照中的状态。

本阶段没有扩大现有个人字段白名单。未来若开放承运商、单号片段、实时来源或更详细履约字段，必须重新明确数据和权限契约，不能借本次授权附带实现。

## 模块和传输

- `orders` 所有并公开最小 reader 与输入/结果 schema。
- `chat-records` 负责工具适用说明、绑定身份、二次白名单投影、整轮来源隔离及工具装配。
- JSON/SSE 共用工具；不新增 HTTP API、SSE 类型、Web 状态、数据库结构或依赖。
- 读取采用现有 MikroORM 只读独立快照模式；不依赖订单完整详情响应，不从聊天模块访问订单 Entity。

## 展示、历史和降级

- 成功、未找到、故障如实区分，故障不能解释为未发货或无订单。
- 模型不得用历史正文补造当前状态、单号、位置或时效。查询结果仅代表读取时刻的本地记录。
- 工具 trace 只保留固定枚举与布尔值，activity 无明细；后续模型历史隐藏原始调用/结果。
- 本轮退出自动记忆和摘要来源，最终聊天正文仍遵循聊天保存规则。来源隔离不是删除用户主动输入的原文。
- 不提供客户端确认通道，也不声称已打开页面或替用户完成任何操作。

## 验收和文档

实现需覆盖契约白名单、只读、本人隔离、两种聊天传输、历史/trace 和来源资格；实际业务验证暂缓，不用静态检查代替。
