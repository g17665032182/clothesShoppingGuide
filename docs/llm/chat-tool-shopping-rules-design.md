# 对话本站购物规则查询设计

## 状态和目的

- 日期：2026-11-17。
- 状态：依据用户直接完成文档并实施及继续确认的授权完成代码集成；业务测试和运行验收暂缓。
- 需求来源：[能力清单](./chat-tool-capability-inventory.md)中的政策/售后知识候选。
- 行为依据：[购物规则契约](../contracts/chat-tool-shopping-rules-crud-contract.md)。

本地履约摘要完成后，下一步让助手能回答“本站如何付款、能否取消、运费多少、有哪些售后能力”。目前没有真实店铺政策或售后系统，因此只发布现有已确认契约中的系统事实，工具命名为 `get_shopping_rules`。

## 用户和流程

1. 已登录用户询问本站购物规则，模型选择对应的一个固定主题。
2. 工具从服务端随版本发布的只读目录返回该主题、安全说明、版本及来源标识。
3. 模型解释当前系统能力，同时保留模拟支付、本地物流、无真实政策来源等关键限制。
4. 若用户转为查询某笔订单，使用已有本人订单工具；需要执行动作时由用户在原界面明确确认。

允许五类主题：shipping、payment、cancellation、fulfillment、after_sales。问题跨主题时可分别查询，不引入无界全文检索或默认批量返回。

## 业务决策

- 信息源复用现有订单、履约摘要及安全契约，不采集外部政策，不把旧设计中的已过时描述装入运行目录。
- 目录只说明本站当前系统实现，不处理商家真实退换资格、退款进度或法律判断。
- 运费仅说明当前本站订单 `0.00 CNY`，不推广到其他商家或未来订单。
- “仅模拟支付”与“未接入售后”须随结果保留，不能误述为真实扣款或不享有售后权利。
- 目录版本只表示部署快照；不伪造政策审核人、商家生效日期、客服电话或售后地址。
- 不新增用户数据读取、订单写权限、导航、表单、后台编辑或数据库结构。

## 来源治理

维护权归仓库订单/聊天模块维护者，使用已有代码审阅和文档流程。每项静态说明有固定来源标识，实际运行目录位于聊天模块的 `knowledge/`；模型传入标识不能触发文件读取。

发布当前既有事实无需引入向量数据库、RAG 框架或搜索库。未来真实店铺政策须先提供经确认的内容、适用对象、版本、生效/失效规则和维护人，再另行设计接入；本阶段不创建假政策占位项。

## 隐私和兼容

- 认证沿用现有聊天；规则对启用普通用户及管理员一致，不接受模型指定身份。
- JSON/SSE 共用工具，不改变既有流事件、Web、订单动作或原查询工具。
- 参数只有枚举；trace 只保存主题、版本和计数，activity 无正文。
- 工具调用/结果从后续历史隐藏；查询整轮退出自动记忆与摘要来源，最终正文继续保存。
- 错误不返回异常，不把未知内容补成政策或承诺。
