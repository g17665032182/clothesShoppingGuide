## 问题与目标

目前系统能够查询本地商品并在聊天中推荐，但缺少可供调用方选择的 SKU 标识，也不能创建或管理订单。商品导入会覆盖库存，尚不具备订单预占与履约的一致性规则。

本轮建立本站订单的后端闭环：选择规格、创建订单、模拟支付、管理员发货、用户确认收货，并保证用户隔离、价格快照、库存一致性和请求防重。

订单会持久化并影响本地目录库存，支付为模拟行为，不产生真实扣款。API 必须明确返回模拟支付标识，不能让调用方误认为已经完成真实收款。

## 用户与权限

| 角色           | 本轮能力                                                             |
| -------------- | -------------------------------------------------------------------- |
| 启用的普通用户 | 查询商品规格；创建、查询本人订单；模拟支付、取消未支付订单、确认收货 |
| 启用的管理员   | 具备本人购买能力；另可查询全部订单、查看详情、整单发货               |
| 禁用账号       | 不能访问受保护 API；订单保留，恢复后可继续本人操作                   |
| 未登录访客     | 不能查询规格或使用订单 API                                           |
| 内部商品维护者 | 沿用商品导入能力，遵守预占库存与下架关闭规则                         |

管理员管理能力不允许代替买家支付、确认收货、任意改价、修改状态或删除订单。

## 核心流程

```text
查询商品规格
  -> 提交 SKU、数量、收货信息和本次提交标识
  -> 服务端校验并整单预占
  -> 待支付（锁价 30 分钟）
  -> 用户模拟支付
  -> 待发货（继续预占）
  -> 管理员填写物流并整单发货（扣减实物库存、解除预占）
  -> 待收货
  -> 用户确认收货
  -> 已完成
```

待支付订单可因本人取消、支付超时或任一商品/SKU 下架关闭，释放整单预占。已关闭订单不可恢复；已支付订单不受后续改价和下架影响。

## 非目标

- 真实支付、第三方支付回调、真实退款及财务结算。
- 聊天下单工具、用户订单页和管理员订单管理页面。
- 购物车、地址簿、优惠券、折扣、运费模板和外币。
- 拆单、部分发货、多包裹、物流轨迹及自动确认收货。
- 订单内容编辑、订单删除、管理员任意改价或修改状态。
- 退款、退货、换货、补货管理后台和独立库存运营系统。

本轮后端 API 接入不授权 LLM 执行订单操作；已有聊天上下文中关于不能下单、不能处理售后的限制继续适用。

## 本次文档提出的细化方案

以下细节没有在访谈中逐项确定，作为文档提案一并审阅，不标记为用户已确认：

| 项目       | 提案                                                                               | 理由                                             |
| ---------- | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| 下单边界   | 每单 1–50 个不同 SKU，每项数量 1–99；重复 SKU 拒绝                                 | 明确请求与整单事务边界                           |
| 收货信息   | 姓名最多 100 字符；手机号为可含前导 `+` 的 6–20 位数字；完整地址最多 500 字符      | 必填并拒绝空白、控制字符，不增加地址簿或地区模型 |
| 物流信息   | 快递公司、运单号各最多 100 字符，trim 后必填                                       | 覆盖手动发货输入                                 |
| 分页       | `page=1`、`pageSize=20`，最大 100；按创建时间倒序、ID 稳定排序                     | 沿用现有分页规模                                 |
| 对外标识   | 规格 API 返回稳定 UUID `skuId`；订单使用 UUID `id` 和服务端唯一 `orderNo`          | 支持准确选规格与运营检索，保留旧聊天商品投影     |
| 下架与导入 | 同一批导入先计算下架整单关闭后的预占，再校验导入库存；任何失败连同订单关闭一起回滚 | 避免下架且库存置零时产生顺序歧义                 |
| 详情与列表 | 列表只返回订单摘要，完整收货信息仅本人详情和管理员详情可见                         | 明确个人信息返回边界                             |

API 字段、错误和幂等细化以待审阅的 CRUD 契约为准；技术文档再确定具体实现机制。

## 验收标准

- [ ] 全部用户接口按当前登录用户隔离，管理员购买能力与管理能力分开授权。
- [ ] 能从规格查询完成多 SKU 下单、模拟支付、整单发货、确认收货闭环。
- [ ] 非法输入、未知字段、缺少认证、越权和不存在资源返回约定错误。
- [ ] 部分 SKU 不可用或库存不足时，不产生部分订单、部分预占。
- [ ] 30 分钟边界、重复提交、并发支付/关闭/下架不会造成状态或库存错乱。
- [ ] 价格、商品和收货快照不被后续商品导入覆盖。
- [ ] 推荐、规格查询和下单使用一致的可售库存语义。
- [ ] 导入及测试 Seeder 不会绕过预占保护，导入失败无部分写入或部分订单关闭。
- [ ] 账号禁用不删除订单；恢复后可以继续本人允许的操作。
- [ ] 迁移保留既有目录、用户、聊天和偏好数据，不执行清库验证。
- [ ] 自动化测试及最终 Smoke Test 明确模拟支付性质，不依赖真实支付服务。
