# 模块开发流程

当用户要求新增业务模块，或实现涉及多个文件、多个层次的功能时使用本 Skill。简单修复、单文件小改动和纯文档编辑不强制使用完整流程，除非用户明确要求。

## 目标流程

将一个不完整的需求推进到可验证的实现：

```text
需求收集
  -> 范围确认
  -> 设计文档
  -> 技术文档
  -> 子代理实施拆分
  -> 子代理开发
  -> 主代理集成
  -> 自动化验证
  -> Smoke Test
  -> 交付记录
```

全程遵守仓库现有架构、包管理器、测试约定、审批门槛，并保护用户已有的未提交修改。

## 阶段一：项目调查

修改代码前必须：

1. 阅读仓库的 `AGENTS.md`、README、包清单和相关模块文档。
2. 检查 Git 状态，不回滚无关改动。
3. 搜索本地依赖和已有模块，优先复用现有能力。
4. 对计划使用的库、框架、SDK 或服务阅读官方文档。
5. 确认运行时、模块系统、编译器、包管理器、数据库和测试约束。

会影响设计的假设必须明确记录，不要把其他项目的约定静默带入当前仓库。

## 阶段二：确认范围

将需求整理为：

- 模块名称和所有权边界；
- 用户操作、API 或事件契约；
- 明确的非目标；
- 数据、权限和持久化要求；
- 兼容性和迁移约束；
- 验收标准。

需求过大时，先收窄为最小可用里程碑。后续能力记录在后续计划中，不提前实现。

## 阶段三：按业务编写文档

同一业务的文档放在同一个目录：

```text
docs/<业务名>/
  <模块名>-design.md
  <模块名>-technical.md
  <模块名>-implementation.md
```

使用 [module-doc-template.md](references/module-doc-template.md) 作为起点：

- 设计文档：说明做什么、边界、API 行为、数据规则和非目标。
- 技术文档：说明目录、依赖、接口、状态、错误、安全和测试。
- 实施文档：说明子代理分工、文件所有权、集成顺序和验收流程。

如果仓库要求先审批设计或范围，在确认前不得开始实现。

## 阶段四：使用子代理分工

对于较大的模块，在协作能力可用且用户或仓库流程要求分工时，使用独立子代理处理边界清晰的任务。常见拆分：

- 依赖、配置和基础设施；
- 核心领域、应用服务和模块接入；
- 测试、测试替身和测试基础设施。

给每个子代理明确说明：

- 需要阅读的设计文档和技术文档；
- 负责修改的文件；
- 禁止修改的文件；
- 需要阅读的本地和官方文档；
- 验收标准；
- 完成后的报告格式。

禁止两个子代理同时拥有同一文件的写权限。根配置、锁文件、应用模块注册和 CI 配置等公共文件默认由主代理维护。

每个子代理完成后必须报告：

```text
修改文件
执行命令
测试结果
未解决风险
越界修改
```

如果任务规模不足以使用子代理，应说明原因，但仍保持文档、边界和验证纪律。

## 阶段五：实现和集成

主代理负责：

1. 解决依赖版本和 API 冲突。
2. 整合子代理修改，不能回滚用户工作。
3. 维护公共文件和跨模块接线。
4. 检查模块边界、导入方向、配置处理和安全行为。
5. 新增必要中文注释，避免无意义逐行注释。
6. 按仓库规则增加测试和包脚本。

优先使用项目已有抽象和成熟库。已有能力足够时，不重复造轮子。

## 阶段六：验证

根据风险执行验证；较大的模块至少运行：

```text
格式检查
类型检查
构建
所属包测试
仓库检查命令
差异检查
```

运行时依赖可用时，再对主要用户路径执行手工 Smoke Test。基础设施不可用时必须明确说明，不能把未执行的检查写成已通过。

至少验证：

- API 和认证授权行为；
- 非法输入和异常映射；
- 密钥不会返回或写入日志；
- 没有意外持久化、迁移或业务耦合；
- 自动化测试不依赖真实凭据，除非明确标记为 Smoke Test。

## 阶段七：交付

最终汇总：

- 已实现和明确排除的范围；
- 修改的文件和模块；
- 子代理分工及报告；
- 依赖和配置变化；
- 验证命令和结果；
- 剩余风险和后续工作。

只完成文档或计划时，不得宣称功能实现完成。
